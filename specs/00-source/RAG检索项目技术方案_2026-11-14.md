## 0. 历次修订记录

### 0.1 2026-11-14 复核修正（保留原始记录）

> 本表为历史记录，其中出现的「零 API 费用」等措辞仅描述当时所讨论的**单个模块**（如 rerank 本地推理），不代表全项目口径；全项目口径以 0.2 为准。

| # | 原表述 | 问题 | 修正后 |
|---|---|---|---|
| 1 | 评测集给每条 query 标 `gold chunk id` | **最严重**。chunk id 依赖切分策略，一旦做「切分策略网格实验」，同一份标注在不同切分下指向不同文本，实验失去可比性 | gold 标在**稳定锚点**上：`doc_id + 章节标题路径 + 原文片段（字符区间）`；评测时映射到当前切分下覆盖该区间的 chunk。父子 chunk 下统一映射到 **parent 段落级锚点** |
| 2 | rerank「几十对候选几秒钟、CPU 无压力」 | 过于乐观。`bge-reranker-base`（278M / 约 1.04–1.5GB）CPU 上 30 候选约 0.7–12 秒不等，随候选数与 passage 长度近似线性 | 「**零 API 费用，但非零延迟**」。从 top-10~20 起做，先用 gold 覆盖率曲线定候选数；各阶段 p50/p95 纳入基线表 |
| 3 | 提过 MiniLM cross-encoder 做轻量替代 | `ms-marco-MiniLM-L-6-v2` 是**纯英文**模型，中文语料会给出「自信但无意义」的分数且不报错 | 中文项目**不用 MiniLM / FlashRank 系列**；用 `BAAI/bge-reranker-base`（XLM-R 多语言），可选 ONNX 量化。rerank 分数是组内相对分，**不可跨模型比较、不可当绝对阈值过滤** |
| 4 | 「FAISS 不支持过滤，所以做前置过滤」 | FAISS 有 `IDSelector` / `IDSelectorBatch` 支持**按 ID 过滤**，只是不支持按元数据字段过滤；该回调在检索最内层循环执行，间接查表有额外开销 | 小库用「先取较大 top-k 再后置过滤」；需前置时维护 `元数据 → id 集合` 构造 selector 并实测开销；过滤是核心需求时换 Qdrant / Chroma |
| 5 | GraphRAG 索引成本「是朴素 RAG 的几十倍」 | 无量级来源的具体倍数，属编造 | 只写定性结论：实体/关系抽取、社区摘要需对同一批文档反复调用 LLM，索引阶段 token 消耗**远高于**朴素 RAG |
| 6 | 「清单里没有任何 JD 要求微调」；「Shopee 面经明确会问…」 | 前者对 JD 不完整的三家（启明合心、AutoAgents、焱法）属外推；后者是第三方公众号整理的面经，不是官方 JD | 分别限定为「**就已核到完整 JD 的岗位而言**」与「**第三方面经整理，非官方要求**」 |

**口径补充**：

- 「零 token / 零调用」在本版中**专指评测回路**：检索指标、网格实验、CI 回归、holdout 全程 0 次 LLM API。
- 本地 embedding / rerank 是**下载权重后 CPU 前向推理**，不发 API 请求、不产生 token 费用，但消耗 CPU / 内存 / 时间（`bge-reranker-base` 约 1.04GB，首次加载有冷启动），不是零算力。
- GitHub Actions **公开仓库 + 标准 2 核 hosted runner** 免费且不限分钟（GitHub 2026 定价公告）；大型 runner 即使公开仓库也计费，评测任务控制在几分钟内。

## 1. 项目定位

**一句话**：一个「可复现、带离线评测的企业文档检索服务」，v1 不是聊天机器人，v0.5 加一个可插拔的演示用生成层，v2 才进入多轮问答形态。

核心卖点是**检索质量 + 可量化评测 + 工程可靠性**。按 Anthropic《Building Effective Agents》的区分，v1 属于 **workflow（确定性代码路径）**，且无 LLM 参与，严格说不是 Agent；所谓「agent」在这里指 **v0.4 的确定性工具编排**。

**为什么是这个形状**

- 清单里百度、鼎帷、猎聘、A13761、快手、小红书、集思的 JD 反复出现「检索召回效果调优与效果评测」「评测集/指标/通过标准」「benchmark 和自动化回归」「可观测」「工具调用链路」「元数据体系」——考核点是工程与评测，不是模型能力。
- 信管（数智化）背景的长板是业务抽象、元数据建模、数据库、流程拆解、文档与汇报；硬拼模型或多轮 Agent 会暴露工程深度。
- 检索命中可用 `gold 锚点是否进入 top-k` 判定，**纯计算、评测回路 0 次 API**，天然绕开配额约束。
- Anthropic 原文亦建议「从最简单方案开始」「很多应用优化单次调用 + retrieval 就已足够」，与本定位一致。

## 2. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 / 工程底座 | Python 3.10+、Git、FastAPI + Pydantic、Uvicorn、YAML 配置 | P0，多家 JD 明确要求；**v0.1 不用 FastAPI，纯命令行** |
| 文档解析 | PyMuPDF(fitz) / pdfplumber、python-docx、markdown-it-py、BeautifulSoup | 保留 PDF、DOCX、MD 混合格式，展示非结构化解析能力 |
| 数据处理 | pandas、**jieba（中文分词）** | BM25 必须分词；英文按空格 split 套中文会退化成按字或按整句 |
| 切分 | 自己实现三种策略（固定长度 / 按标题递归 / 句子滑窗 + overlap） | 不直接用 LangChain 封装，否则讲不清切分机制 |
| Embedding | sentence-transformers + `BAAI/bge-small-zh-v1.5`（约 95MB，中文）；横向对比 `text2vec-base-chinese`、`m3e-base` | 全本地推理，0 次 API；向量 L2 归一化后用内积等价余弦 |
| 向量索引 | `faiss-cpu`：`IndexFlatIP` + `IndexIDMap2` | 万级 chunk 精确检索足够；**务必归一化，否则 L2 排序 ≠ 余弦排序** |
| 稀疏检索 | `rank_bm25`（或 BM25S）+ jieba | 兜住编号、术语、专名等向量易糊掉的精确匹配 |
| 融合 | RRF：`score(d) = Σ 1 / (k + rank_i(d))`，k 常取 60 | 用排名而非分数，免去两路量纲归一化 |
| Rerank | `BAAI/bge-reranker-base`（ONNX 量化可选） | cross-encoder 本地推理；不用英文 MiniLM（见 0.1 #3） |
| 元数据存储 | SQLite（文档表、chunk 表、parent 映射、评测集、trace、run 记录）；**建表 SQL 与变更脚本按 SOP `06-schemas/` 补齐** | 信管主场；对应鼎帷「数据标签与元数据体系」 |
| 服务接口 | `/search`、`/eval`、`/ingest`、`/trace`（v0.4）；`/ask`（v0.5） | REST/JSON，带 JSON Schema 的工具契约 |
| 展示 | Streamlit 单页（v0.5） | 不啃 React/Vue |
| 评测 / 可观测 | 自建 `eval.py`、JSONL trace、p50/p95 计时、bootstrap 置信区间 | 纯计算与日志，**评测回路 0 次 LLM** |
| CI / 复现 | GitHub Actions（公开仓库标准 runner）、固定随机种子、模型版本与评测集哈希写入 `run_id` | 一键复现所有数字 |
| **生成层 `LLM_BACKEND`（v0.5）** | 云端 LLM API（低配额，默认）或本地 Ollama + Qwen2.5:1.5B（二选一） | **唯一使用 LLM API 的模块**；不进指标、不进 CI；若改纯本地，配额约束降级为耗时约束 |
| **会话记忆（v2）** | 会话 id + SQLite 历史表 + 规则式指代替换（0 API 起步），LLM 摘要压缩为进阶 | 见第 7 节；**与检索评测回路隔离** |

**明确不引入**：LangChain 高层封装作为唯一实现、GraphRAG、模型微调 / embedding 训练、LLM-as-Judge 全量回归、用 LLM 造 gold 标注、每条 query 都做的 HyDE / 查询改写、多轮 ReAct / 自我反思、自动 Prompt 优化、分布式与 K8s、云端向量服务、鉴权与多租户。

**交付说明文本规范**（对后续开发的约束）：本条为 SOP 规则 #11 在本项目的落地说明，**不另立清单**。适用对象、禁用写法、必须保留项、路径边界、检查方式与判断准则一律以 SOP 附录 C 为唯一判定依据；交付说明文本只写功能、约束、接口、参数、失败处理与运行依赖。检查方式与门禁要求按附录 C.4 检查方式及 SOP 步骤 6/7 执行。规则判定以当前 SOP 附录 C 为准；归档副本不承载判定，归档时记录所依据的 SOP 版本与日期。

## 3. 功能模块清单（含版本归属）

### A. 检索主链

| 模块 | 做什么 / 为什么有效 | 边界与易错 | 版本 |
|---|---|---|---|
| A1 解析与统一 JSON | PDF/DOCX/MD → 统一结构，带 `doc_id、标题路径、来源、日期、类型` 元数据 | 表格与扫描件单独标记；保留原始字符区间供锚点映射 | v0.1 简版 / v0.3 完整 |
| A2 三种切分策略可切换 | 切大则主题糊、切小则语义断；提供可对比实现 | 换策略后 chunk id 全变 → 必须靠锚点映射评测 | v0.1 一种 / v0.3 三种 |

| A4 标题路径注入 | 把「第3章 > 3.2.1」拼进 embedding 文本，给向量显式主题锚点 | 路径过长稀释正文，需限长与权重 | v0.3 |
| A5 BM25 + 向量混合 + RRF | 两路盲区不重叠：BM25 怕同义、向量怕编号术语 | 中文必须分词；RRF 的 k 与两路权重纳入网格 | v0.2 |
| A6 本地 rerank | cross-encoder 让 query 与 chunk 在注意力层交互打分，精度高于 bi-encoder | 只对 top-10~20 做；候选数由覆盖率曲线定；分数只可组内比较；延迟必须实测 | v0.3 |
| A7 查询归一化与规则路由 | 简繁/全半角/单位归一、领域词典、编号保护；按「含时间/含编号/并列型」动态调两路权重 | 同义扩展过度拉低 precision，需量化「Recall↑ / nDCG↓」取舍 | v0.3 |
| A8 元数据过滤 + 降级路径 | 按时间/类型/项目缩小候选；三条兜底：向量库异常→退 BM25、rerank 超时→返回融合排序、过滤 0 结果→放宽并记录 | 前置过滤用 IDSelector 有间接查表开销；小库优先后置 | v0.4 |

### B. 评测与可观测（评测回路全程 0 次 API）

| 模块 | 做什么 / 为什么有效 | 边界与易错 | 版本 |
|---|---|---|---|

| B6 延迟与资源基线 | p50/p95 各阶段耗时、索引体积、内存峰值、QPS | 数字必须能一键复现 | v0.3 |

### D. 生成层（v0.5 启用，唯一使用 LLM API）

- **`/ask` 最小生成**：检索 top-k 拼进 Prompt 生成答案，手动演示 10~20 次。**不进任何指标、不进 CI、不随评测集条数线性增长**。
- **Prompt 模板版本化**：此时是真实模块（不再是空壳），独立文件 + 版本号，改动记 `PROGRESS.md`，按 SOP 规则 #7 不触发全量回归。
- **引用可追溯检查**：纯字符串匹配检查输出引用 id 是否真在 top-k 里（规则式幻觉检测，0 次 API）。
- **失败案例批量归因**：把 15~20 条 bad case 的 trace 一次长调用喂给模型，产出归类与改进假设；**假设由人固化成规则**（A7 词典、切分规则），LLM 不进运行时。
- **README 中的指标口径说明**：检索指标为离线计算，生成层不参与任何指标；生成质量未做量化评测，评测边界划在检索层。

## 4. 开发边界

### 4.1 v1 明确不做（含理由与面试答法）

| 不做 | 原因 | 被问到时的回答 |
|---|---|---|
| 把生成质量当检索指标 | `答案正确率 = f(检索质量, 模型能力)`，两个自变量无法反推：弱模型会因读不懂已召回内容而**低估**检索，强模型会靠参数化知识绕过检索而**高估**检索 | 「评测边界划在检索层，比的是正确片段的排名位置，不是答案对不对」 |
| 多跳 / 依赖型推理 | 第二步依赖第一步结果，需多轮检索与生成 | 「单跳检索；多跳归到已知限制」 |
| LLM 自主规划（ReAct / 自我反思） | 每轮都要调用 LLM，按轮数放大 | 「用确定性状态机替代规划，工具契约、编排、失败恢复照做」 |
| 知识图谱 / GraphRAG | 建图需对全库反复 LLM 调用，且需多跳题集验证收益 | 「索引阶段调用量远超朴素 RAG，与配额约束冲突，单跳场景收益也不成立」 |
| 微调 / 训练 embedding | 需 GPU、训练数据与评测闭环；就已核到完整 JD 的岗位而言均未要求 | 「判断瓶颈在召回不在生成，预算投到检索质量和离线评测」 |
| LLM 造 gold 标注 / LLM-as-Judge 全量回归 / HyDE / 每条 query 都做的查询改写 | 调用量是**乘法结构**：81 组 × 100 条 × 生成 × judge 可达万次量级；且破坏可复现性 | 「评测集人工标注、指标纯计算，所以全部结果可一键复现」 |
| 分布式、云端向量库、鉴权、多租户 | 与「单机 CPU 可跑」目标冲突 | 「规模边界内用不上」 |

### 4.2 v2 明确要加（用户已决定）

**跨会话历史记忆与多轮问答形态**。v1 无状态不是遗漏，是设计选择；详细设计见第 7 节。**不得**把本条理解为「永久不做」。

### 4.3 规模与合规边界

文档量几千篇以内、chunk 十万以内、单机 CPU、内存目标 < 4GB、并发个位数、无 SLA 承诺。超过才需要 IVF/HNSW、原生过滤向量库与服务化部署。

只用可公开分发、许可证清晰的文档，README 标注来源与许可证；不上传含个人信息、学校内部资料或企业机密的材料；trace 日志不记录敏感原文。对应鼎帷 JD 的「数据安全与保密意识」。

### 4.4 低配额边界（准确定义）

- **评测回路 0 次调用（铁律）**：检索指标、网格实验、CI 回归、holdout、参数选型，全部纯计算。
- **LLM 只出现在 v0.5 的演示与诊断**：约 20~30 次，单次调用、不随评测集条数线性增长。建议分配（总上限 50 次）：演示 ≤20 次、批量归因 ≤5 次、评测集 query 候选 1 次、预留缓冲 ≥30%。
- **配额硬数字写进 `specs/constitution.md`**：评测回路 0 次 / 总调用上限 50 次 / 单次超时 30 秒 / `/ask` 带熔断。
- **本地推理不是零算力**：embedding 与 rerank 消耗 CPU / 内存 / 时间，但不占 API 配额。
- 若「几百次」指的是**速率限制**而非总量上限，不建议靠拉长实验周期分批跑：周期一长模型版本、评测集、代码都会漂，`run_id` 守不住可复现性。

## 5. 版本路线（与 SOP 第八部分一致）

**版本命名约定**：`v0.1`~`v0.5` 是首个可交付大版本 **`v1`** 的迭代步；**`v2`** 是下一大版本（记忆与多轮问答）。全文出现「v1」时指 v0.1~v0.5 整体，出现「v0.x」时指单个迭代步。因此「v1 不做生成质量评测」与「v0.5 有演示用生成层」不矛盾：前者指不评测，后者指可演示。

| 版本 | 新增 | 生效依据 | LLM API |
| --- | --- | --- | --- |
| **v0.1 最小闭环** | 2 篇文档、1 种切分、向量检索、30 条人工锚点评测集、`eval.py` 打印 Recall@5 / MRR（**纯命令行**） | 同一 `run_id` 连跑两次数字完全一致；锚点 100% 可映射 | 0 |
| **v0.2 可信 A/B** | BM25 + jieba + RRF、评测集补到 100 条 + 20% holdout、Trace 日志、2~3 组实验 | 融合相对**重跑的基线** Recall@5 提升，holdout 不翻转，trace 能定位 ≥3 类失败 | 0 |
| **v0.3 检索质量** | 三种切分 + 父子 chunk + 标题路径、本地 rerank（先跑覆盖率曲线）、bootstrap 区间 | rerank 前后 MRR / nDCG@5 差值 + p95 延迟代价表；区间重叠不算提升 | 0 |
| **v0.4 工程化** | FastAPI 四接口 + JSON Schema、元数据过滤 + 三条降级、增量入库/去重/质量报告、确定性状态机编排、CI 回归 | Schema 校验通过、关掉向量库能退到 BM25、CI 复现同一数字 | 0 |
| **v0.5 交付演示** | Streamlit、README/架构图/决策记录、`/ask` 生成层、失败案例批量归因 | 冒烟脚本可重复执行且自动清理、每个数字能说清来历 | 约 20~30 次 |
| **v2 记忆与问答形态** | 跨会话记忆、多轮问答（第 7 节） | 另行定义多轮对话评测串 | 按新配额重新评估 |

**v0.1 三件不能省**：稳定锚点（不是 chunk id）、`run_id`（固定种子 / 模型版本 / 评测集哈希）、事先切好并封存的 holdout。事后补做要重跑全部实验。
**最小循环 ≠ 最小产品**：v0.1 不建 FastAPI / Streamlit / Docker，先把数字跑对。
**版本间同一把尺子**：评测集、指标定义、`run_id` 口径不变。**易错点**：v0.1 用 30 条、v0.2 补到 100 条时基线数字会变，必须在新集上重跑一次 v0.1 配置作为新基线，不能沿用旧数。
**推进门槛**：指标可复现 + 代码可运行无半成品 + 决策写入 `CHANGELOG-DECISIONS.md`，三条齐才进下一版（SOP 规则 #9）。

**v0.1 起步五步**：选 2 篇许可证清晰的公开中文文档 → `ingest.py`（解析 → 固定长度切分 → chunk 表存 `doc_id / 标题路径 / 字符区间`）→ 人工标 30 条 query + gold 锚点存 CSV → `eval.py`（`bge-small-zh` 向量化 → `IndexFlatIP` → top-5 → 锚点映射 → 打印指标）→ `config.yaml` 固定种子与模型版本。跑通标志：同一命令连跑两次输出完全一样。

## 7. 历史记忆 v2 设计（已决定要加）

### 7.1 为什么 v1 无状态

A/B 实验要求 `f(query, config)` 是纯函数，同一 query 恒返回同一结果；引入会话状态后变成 `f(query, config, session_state)`，基线与实验不可比。SOP 的 P1#9 在 v1 的答案是「**不存、无失效策略**」，同时在此写明 v2 规划——**不是留空**。

系统里已有「历史记录」但无「历史记忆」：B4 Trace 日志、C2 精确缓存、B8 run 记录都存过去发生的事，但**不参与下一次决策**；缓存命中返回的是同一结果（幂等），不是结合上下文改写的响应。

### 7.2 触发条件

产品形态从「单轮检索服务」变为「多轮问答助手」，用户会追问：指代消解（"它多少钱"）、省略补全、跨轮约束（"只看 2025 年的"）、偏好延续。此时才加。

### 7.3 设计约束（不可违反）

1. **隔离**：记忆只作用于多轮问答层；`/search`、`/eval`、CI 回归**永远无状态**。`run_id` 增加 `stateless_mode=true`，评测时记忆模块强制关闭。
2. **最小实现优先**：会话 id + SQLite 存 `(query, top-k, 选中 chunk)` + 规则式指代替换 → **0 次 API**；LLM 摘要压缩历史属进阶，须重新评估配额。
3. **评测要重建**：样本从「单条 query + gold 锚点」变为「对话串 + 每轮 gold 锚点」，工作量与调用量约 ×3~5；**按会话切分 holdout**，否则同一会话轮次会泄漏到训练集。
4. **不把生成质量当检索指标**：弱模型低估、强模型高估（见 4.1 第一行）。检索指标始终用纯计算的 Recall / MRR / nDCG。
5. **变更分级**：新增记忆属「架构 + 能力边界」重大变更，走变更单、更新 `09-state.md`、重新过 G2。
6. **成本机制**：烧 API 的不是"存历史"，而是把前 N 轮拼进上下文（token 随轮数累加）、超窗摘要、让模型判断该记什么；真正烧不起的是多轮评测串。

## 8. 验收标准

不看用了多少技术，只看能否不看稿回答：

- 某个数字从哪来、能否一键复现；
- rerank 让 MRR 从多少到多少、在**哪类 query 上反而变差**；
- 为什么切分是 512 而不是 256；
- 向量库挂了系统怎么表现；
- 为什么没用知识图谱、没做微调；
- 评测集换一种切分策略后为什么仍然有效；
- 为什么 v1 没有记忆、v2 加记忆时如何保证 A/B 仍可比；
- 为什么评测回路 0 次 API、那点配额花在了哪里。

答得上来即达标；答不上来说明加的是功能不是能力。

**转 EARS**：本清单在 Specify 阶段逐条转成带编号的 EARS 条款（如「当 `/search` 收到查询时，系统应当返回 top-k chunk 及其锚点与分数」「如果向量检索异常，则系统应当退回 BM25 并记录 `FALLBACK_BM25`」），供 `tasks.md` 引用。
