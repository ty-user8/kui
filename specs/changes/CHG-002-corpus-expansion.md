## 1. 背景与原因

v0.1 按方案只取 2 篇文档，实测规模如下：

| 项 | v0.1（2 篇） | 全量（150 篇） |
| --- | --- | --- |
| 正文字数 | 8116 | 1162584 |
| 条款数 | 114 | 9865 |
| chunk 数（512 / overlap 64） | 约 18 | 约 2595 |
| 占全量比例 | 0.7% | 100% |

问题在指标区分度：18 个 chunk 下 Recall@5 的随机基线约 28%，两路检索的差异会被小样本噪声吞掉。v0.2 要证明「BM25 + 向量 + RRF 优于单路」，候选池只有 18 个 chunk 时该结论不可信，也无法做参数网格。

v0.1 保持 2 篇不变：它的职责是跑通闭环与校验可复现，不用于判断质量。

## 2. 变更内容（三项分列）

### 项一 · 范围变更：v0.2 语料由 2 篇扩为 150 篇

- `corpus/docs` 全量入索引，只读，不新增文档、不改 manifest、不触发 CHG-001 的格式边界。
- v0.1 的 2 篇子集保留为固定可复现配置（`config.yaml` 的 `corpus.v01_subset`），用于回归对照。
- 该变更写入 `02-scope.md` §1 版本范围表 v0.2 行。

### 项二 · 评测集规模：30 → 100 条（含 20 条 holdout）

- v0.1 的 30 条全部保留：锚点是 `doc_id` + 字符区间，与语料规模无关，扩语料不使旧锚点失效。
- 新增 70 条分布在其余文档，其中 14 条为 holdout，使 holdout 合计 20 条（6 + 14）。
- **前置条件**：`candidate` 只指 `query`——由 Agent 起草、用户确认措辞。`anchor_text` 与 `char_start` / `char_end` **一律由回填工具从 DOCX 基准文本抽取**（输入 `doc_id` + `article_no`，按 `01-requirements.md` 5.3 切片并回切校验），人工只做确认，Agent 不得起草 gold，也不得以任何生成式手段补全锚点。`anchor_status` 只有用户可改为 `confirmed`；未确认的案例不进入指标，其数量在输出中单列。
- 该变更写入 `02-scope.md` §4 与 `01-requirements.md` REQ-033。

### 项三 · 实现细节（不入范围变更）：`run_id` 增加语料指纹

- 内容：`run_id` 追加语料指纹字段，取值 `manifest.json` 的 SHA-256 与入索引文档数。
- 理由：语料变更后若 `run_id` 不变，两次运行语料不同却标同一标识，可复现性失效。
- 处置：只在 `CHANGELOG-DECISIONS.md` 记一条决策（D-012），不写入 `02-scope.md`，不走范围门禁。

### 项四 · 口径补充：`anchor_text` 回切时保留段内 `\n`

- **问题**：8 篇含 `w:br` 软换行（13 处，其中 3 篇的 4 段位于标题折行），`paragraph.text` 中表现为 `\n`。若 CSV 写入或读取时 strip、或把 `\n` 替换为空格或字面量 `\\n`，回切比对会把这些案例误判为「标注失效」。
- **口径**：**原样保留**。基准文本保留 `\n`（`01-requirements.md` 5.3.1），`anchor_text` 同样原样保留；CSV 读写不得 strip、不得替换 `\n`，写入用标准 CSV 引号包裹（`csv` 模块默认行为），读取后不做任何清洗。
- **理由**：与基准保持一致，规则只有一条；若改为统一剔除，需要在基准侧与锚点侧同时做变换，反而多出一处可偏离的口径。
- **落点**：批准后并入 `01-requirements.md` 5.3.4 第 2 条（锚点回切比对）。

### 项五 · 口径补充：表格排除的守恒校验

- **字段**：质量报告（C1，v0.4）记 `excluded_chars` 与 `excluded_ratio`；`documents` 表同步落 `excluded_chars` 与 `chars_total`。
- **守恒断言**：`基准字符数 + excluded_chars = 可提取总字符数`。可提取总字符数按 `01-requirements.md` 5.3.1 的口径统计（段落文本 + 表格单元格文本 + 已计入的制表符与软换行），三部分不得重叠计数。
- **标注约束**：v0.2 新增 70 条 query **不得指向表格内内容**（《电力安全事故应急处置和调查处理条例》的事故分级表）；若要检索该表，先出变更单把表格纳入基准。
- **落点**：`06-schemas/` 的 `documents` 字段、`12-release-checklist.md` 的质量报告项。
- **影响**：全量语料仅 1 篇含表格，该文档 `excluded_chars ≈ 2205`、`excluded_ratio ≈ 25%`（文档内部比例，非全库比例）。

### 3.2 波及的模块与文件

- `src/` 的 `ingest`：支持「全量目录」与「显式文件清单」两种输入，后者对应 v0.1 子集。
- `config.yaml`：新增 `corpus.v01_subset`（2 篇）与 `corpus.full`（`corpus/docs` 全量）两组定义与默认值。
- `eval.py`：分母随评测集条数变化，逻辑不变；`unmapped` 计数口径不变。
- 标注辅助工具：需支持跨文档按 `doc_id` 定位与导出候选句，而非只在 2 篇内定位。

### 3.3 波及的接口与数据结构

- 无 Schema 变更。`chunks` 表行数由约 18 增至约 2600；`documents` 表由 2 行增至 150 行。
- `run_id` 字段结构增加语料指纹（项三），解析规则需同步更新。
- `/ingest`（v0.4）请求体需能表达「子集」与「全量」，属新增可选字段，不破坏既有契约。

### 3.4 需要更新的评测用例

- 新增 70 条 `version_introduced=v0.2`，其中 14 条 `split=holdout`。
- 原 30 条不改锚点，仅复核 `anchor_status`。
- v0.2 起 100 条全部为 `confirmed` 后才计算指标；未确认数与 `unmapped` 分开计数。

### 3.5 对成本／性能／安全的影响

| 维度 | 影响 |
| --- | --- |
| LLM 调用 | 0 次，无变化 |
| embedding 计算 | 入索引 chunk 数由约 18 增至约 2595（约 144 倍）；此处「144」是 **chunk 数倍数**，不是文档数——文档数由 2 篇增至 150 篇，即新增 148 篇。CPU 首次向量化耗时须实测后写入 B6 表，本单不预设数值 |
| 索引体积 | **估算值**：约 2595 × 512 维 × 4 字节 ≈ 5 MB（不含 FAISS 索引头与 ID 映射表）。以 B6 实测表为准，实测后回填本行 |
| 评测耗时 | 100 条 query 的 top-k 检索在 CPU 上仍为秒级 |
| CI（v0.4） | 需缓存 embedding 结果，否则每次重算会拖长回归 |
| 标注工作量 | 30 → 100 条，全部需人工确认，是本次变更的主要人力成本 |
| 安全 | 无变化：语料仍只读、公开法规、无 PII |
