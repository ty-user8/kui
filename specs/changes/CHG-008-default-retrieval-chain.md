# 变更单 #008：默认检索链对齐基线（`use_bm25` 由 `false` 改为 `true`）

- 日期：2026-11-20
- 发起方：开发方（T-023 实现四接口时发现默认链与 `CHG-007` 基线不一致）
- 状态：**已完成**（本单为追认：变更已在 T-023 落地并经用户口头认可，本单补契约与缺口登记）

**状态流转说明**：本单在起草前变更已实施并验证，故流转跳过「执行中」——2026-11-20 用户认可方向（「接口默认链须与 CHG-007 基线 hybrid 一致」）后补单追认，同日转「已确认」并因改动已毕转「已完成」。如实记录，不补造中间态。

## 背景

`config.yaml` 的 `retrieval.use_bm25` 自 v0.1 起一直是 `false`，而 v0.2 起基线检索链是「向量 + BM25 融合」（`CHG-007` 确认的 `r5e4a62714526`，现为 `r6c23283f2577`）。两者此前靠人工记忆弥合：命令行 `eval` 必须显式带 `--retriever hybrid` 才与基线一致，不带就跑单路；v0.4 的四个接口按配置取值，不翻这个开关的话 `/search`、`/eval` 默认退成单路，与基线不是同一套数。

这不是新增功能，是把**配置纠正到既有决策**，但它改变了对外可见的默认行为（接口默认链、命令行默认链），因此按契约变更补单追认。

## 变更内容

| 项 | 变更前 | 变更后 |
| --- | --- | --- |
| `config.yaml` → `retrieval.use_bm25` | `false` | `true` |
| 接口 `/search` 默认链 | 向量单路（`path=dense`） | 向量 + BM25 融合（`path=fused`） |
| 接口 `/eval` 默认指标 | 单路口径 | 与 `CHG-007` 基线逐项一致 |
| 命令行 `eval` 不带 `--retriever` | 单路 | 融合（与基线一致） |
| `retrieval.use_rerank` | `false` | `false`（**未动**，v0.3 三处否决保持不启用） |

同一 `run_id` 下两种链的实测差距（150 篇 / 2704 chunk / 100 条全量，同一索引与用例）：

| 链 | Recall@1 | Recall@3 | Recall@5 | MRR | nDCG@5 |
| --- | --- | --- | --- | --- | --- |
| 融合（`true`，基线） | 0.5600 | 0.8600 | **0.9000** | **0.7045** | **0.7543** |
| 单路（`false`，旧默认） | 0.4800 | 0.7300 | 0.8400 | 0.6200 | 0.6751 |
| 差值 | −8.00pt | −13.00pt | −6.00pt | −8.45pt | −7.92pt |

dev 80 条上单路为 R@5 0.8375 / MRR 0.6121，与 `evals/experiments-v0.3.md` 的 A 组一致，说明差距来自链路而非索引或数据。

## 缺口登记：`run_id` 规范串不含 `use_bm25`

`build_run_id` 的规范串是 `seed;model;chunk;topk;cases;corpus;docs;nv` 八段，**不含** `use_bm25`、`use_rerank`、`rrf_k`。后果：

1. 改这两个开关不会改变 `run_id`，也不会自动加 suffix；
2. 同一 `run_id` 下可能并存两套指标，只差在 `attempt-N` 目录；
3. 现有可区分手段（均已存在，不需新增字段）：
   - `data/runs/<run_id>/attempt-N/meta.json` 的 `use_bm25`、`rrf_k`、`candidate_k`（T-008 起写入）；
   - 同一目录 `metrics.json` 的 `retriever` 字段（`hybrid` / `dense`）；
   - 命令行 `--run-suffix` 手工区分（如 `-dev-dense`）。

**处置二选一**（本单记录，不自行扩权）：

| 选项 | 做法 | 代价 | 本次是否采用 |
| --- | --- | --- | --- |
| A 记入 runs 元数据 | 靠 `attempt-N/meta.json` 与 `metrics.json` 的既有字段区分，不新增 `runs` 表列、不改 Schema | 无；缺点是查 `runs` 表时看不到链，需要翻文件 | **采用**：现状已满足，字段自 T-008 就在写，只是此前没在文档里点明这是唯一区分手段 |
| B 下个大版本进规范串 | 把 `use_bm25`／`use_rerank` 纳入 `build_run_id` 规范串 | 所有 `run_id` 改变 → 基线必须重定，历史 run 目录与新 id 不可比 | 不采用：本单明确「不改规范串、不换基线」，留作下一大版本的候选 |

## 回滚方式

1. 把 `config.yaml` 的 `retrieval.use_bm25` 改回 `false`，重启服务（接口每次请求读配置，命令行无需重启）。
2. 预期回落：`/search` 的 `path` 变 `dense`、`score` 变余弦；`/eval` 与命令行默认指标回到上表「单路」列（R@5 0.8400、MRR 0.6200）。
3. `run_id` 与基线**不受影响**（规范串不含该字段，基线数值也未因本单改变），无需重跑基线；仅需在 `PROGRESS.md`／`HANDOFF.md` 记一次回滚原因。
4. 若已发布镜像，回滚配置后需重新发布包，避免运行中的实例仍持旧值。
